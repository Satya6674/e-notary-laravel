# E-Notary — Digital Notarization Management Prototype (Laravel)

> **Independent academic / college demonstration prototype.**
> E-Notary is **not** a government service. It is **not** affiliated with, authorised by or endorsed by any
> government body, court or bar council, and nothing it produces is legally valid. Certificates and PDFs
> generated by the application are marked *"Not legally valid. Not a notarised document."*

**Live demonstration:** <https://enotary.alwaysdata.net>

E-Notary is a role-based web application, built with Laravel 12, that models how a digital notarization
office could be run online. Citizens apply for notarization services and upload documents. Admin
approves Notaries, and approved Notaries review requests and complete them. Every important action is
recorded in an append-only audit log.

## Problem statement

Getting a document notarised usually means several visits to an office, paper forms that are hard to track,
and little visibility into where a request stands. Records of who did what, and when, are often incomplete.
This project explores how such a workflow can be digitised: a single portal where applicants submit
documents, verified professionals review them, and administrators supervise the whole process. Access
control, verification and auditability are designed in from the start.

## Objectives

- Provide separate, access-controlled portals for **Citizens**, **Notaries** and **Admin**.
- Verify every applicant's email address before they can use the portal.
- Ensure that no Notary can act until an **Admin has approved** them.
- Track each notarization request through clear states, from submission to completion.
- Store uploaded documents privately, with integrity hashes and version history.
- Protect administrative actions with two-factor authentication and step-up re-authentication.
- Keep an append-only, database-enforced audit trail of security-relevant events.
- Make it impossible to mistake the prototype for a legally valid or government service.

## Key features

| Area | What is implemented |
| --- | --- |
| Accounts | Registration (Citizen or Notary), email verification by 6-digit code or signed link, password reset by email, profile and photo, English / Hindi / Punjabi interface |
| Citizen portal | Service catalogue, guided application with saved drafts, document upload, request tracking, resubmission after a correction request, withdrawal |
| Notary portal | Pending-approval page until approved, assigned-request queue, approve / reject / request correction / complete, document download, reports |
| Admin portal | Dashboard and analytics (CSV, XLSX, PDF export), user management, Notary approval, request assignment and decisions, document management, contact messages, audit log, service-catalogue editing, security centre (permissions, privacy requests, incidents), email delivery log |
| Shared | Appointments, support tickets with attachments, in-app notifications, privacy centre (requests, consent, data export) |
| Documents | Application receipt, summary, review report and demonstration certificate as PDFs (mPDF) with QR codes. Public certificate lookup at `/verify/{code}` shows no personal details |
| Account safety | Account deactivation and restoration, Admin-reviewed account recovery, email-address replacement with confirmation link, manual verification and time-limited temporary access granted by Admin |
| Operations | Artisan commands for first-Admin creation, deployment checks, health and mail status, data retention clean-up, and a scheduler with a safe mode |

## Roles

| Role | Can do | Cannot do |
| --- | --- | --- |
| **Citizen** (`public`) | Register, verify email, apply for services, upload documents, track and withdraw own requests, book appointments, open support tickets | See any other user's data or reach Notary/Admin pages |
| **Notary** (`notary`) | After Admin approval: work on requests assigned to them, approve, reject, request corrections, complete, view reports | Act before approval, or see requests not assigned to them |
| **Admin** (`admin`) | Approve or reject Notaries, assign requests, manage users, documents, services and settings, review audit logs and security | Perform sensitive actions without a recent second-factor confirmation |

Access is enforced by route middleware (`admin`, `notary`, `role:*`, `portal`, `verified`, `account.choice`,
`schema.ready`) and by model policies in `app/Policies`.

## Registration and verification

**Citizens**

1. They sign up from the home page with name, email, a 10-digit mobile number and a password. The password policy is enforced by `App\Support\PasswordPolicy`, including bcrypt's 72-byte limit.
2. A verification email carries both a **6-digit code** and a **signed link**. Either one verifies the address. Codes expire, are rate-limited, and lock after repeated wrong attempts.
3. SMS verification of the mobile number (MSG91) is implemented but **off by default**
   (`CITIZEN_MOBILE_VERIFICATION_REQUIRED=false`, `MSG91_ENABLED=false`). Without SMS, registration is
   complete once the email is verified.

**Notaries**

1. They register the same way, with the Notary role, and verify their email.
2. The account then waits on `/notary/pending`, with no access to any work.
3. An **Admin must approve** the application (`/admin/notaries`). Approval and rejection are audited and
   require Admin step-up. Only an approved Notary reaches the Notary dashboard.

There is no web route that creates an Admin. The first Admin is created at the server console with
`php artisan enotary:admin-create`. The password is typed at a hidden prompt, and the command refuses to run
if an Admin already exists.

## Admin security and MFA

- **TOTP two-factor sign-in** (RFC 6238: SHA-1, 6 digits, 30-second step) works with any authenticator app.
  It comes with **8 one-time recovery codes**, which are stored hashed. Failed attempts are limited: 5 tries,
  then a 15-minute lock.
- `ADMIN_MFA_REQUIRED=true` makes enrolment mandatory. An Admin without MFA can then reach only the setup
  page. If the MFA check cannot be performed, access fails closed.
- **Step-up re-authentication.** Sensitive actions, marked by the `admin.reauth` middleware, need a fresh
  authenticator or recovery code. "Fresh" means within `ADMIN_REAUTH_MINUTES`, which defaults to 10. These
  actions include changing a user's role, email or password, deleting or restoring accounts, Notary
  decisions, request decisions, exports and document downloads.
- **Protected accounts**: the addresses in `PROTECTED_ACCOUNTS` (validated, comma-separated) cannot be edited,
  deactivated or deleted by another Admin. Nothing is protected while it is empty, and `enotary:deploy-check` warns about that.
- Console recovery tools: `enotary:admin-reset` (lost password) and `enotary:admin-mfa-reset` (lost authenticator).

## Document and request workflow

```
Citizen                        Admin                         Notary
───────                        ─────                         ──────
choose service ─► draft ─►
submit request  ───────────►  pending
                              assign to Notary ─────────►   assigned
                                                            ├─ request correction ─► Citizen resubmits ─┐
                                                            ├─ reject                                   │
                                                            └─ approve ─► complete ◄────────────────────┘
track status / download receipt, summary and demo certificate (PDF)
```

- Request states: `pending`, `assigned`, `correction_requested`, `approved`, `completed` and `rejected`
  (`App\Models\NotaryRequest`). The Citizen can withdraw a request.
- Uploads: PDF, JPG, PNG, DOC or DOCX, up to 10 MB. Both the file content and its extension are checked.
  Files are stored on the **private** disk, never under `public/`, and served only through
  authorised controllers.
- Each stored file has a **SHA-256 hash**. Replaced and corrected files are kept as a **version history**.
- Completed requests receive a verification code. Anyone can look the code up at `/verify`, which shows the
  certificate's status and no personal data.

## Demonstration safeguards

- Every generated PDF carries the footer **"Not legally valid. Not a notarised document."** Sample PDFs are
  marked **"SAMPLE ONLY. NOT LEGALLY VALID."**
- `App\Support\DemoClaims` refuses Admin-published text (the site notice and service descriptions) that would claim
  legal validity or government authorisation or affiliation. A test guards the published pages.
- The Citizen portal footer shows an *"Independent Prototype | For Evaluation Only"* notice, and the About,
  Terms, Privacy and Disclaimer pages explain the prototype status.
- All pages send `X-Robots-Tag: noindex, nofollow`, so the demo is not indexed by search engines.
- Outbound email is **off by default** (Safe Preview). Real mail is sent only when `LIVE_MAIL_ENABLED=true`,
  and even then only for a fixed allow-list of notification types defined in code.

## Architecture

```
Browser ──HTTPS──► Web server (Apache / php artisan serve)
                    │
                    ▼
            Laravel 12 application
            ├─ routes/web.php ─► middleware (auth, role, verified, admin MFA, step-up,
            │                     throttling, security headers, locale)
            ├─ Controllers      app/Http/Controllers/{Admin,Auth,Notary,User,…}
            ├─ Services         app/Services (applications, OTP, MFA, delivery log, recovery, …)
            ├─ Policies         app/Policies (per-record authorisation)
            ├─ Models           app/Models (Eloquent)
            ├─ Notifications    app/Notifications → database queue → SMTP
            ├─ PDF rendering    app/Support/PdfRenderer (mPDF) + resources/views/pdf
            └─ Console          app/Console/Commands + scheduler (app/Console/ScheduledTasks.php)
                    │
                    ├──► MySQL / MariaDB (data, queue, cache, sessions, audit triggers)
                    └──► storage/app/private (uploaded documents, never public)
```

## Database design

There are 44 migrations in `database/migrations`. The main tables are:

| Table | Purpose |
| --- | --- |
| `users` | All accounts, with role (`public`, `notary`, `admin`), verification timestamps, Notary approval fields, deactivation |
| `notary_requests` | Service applications and their workflow state, assignment and decisions |
| `documents` | Uploaded files: private path, SHA-256 hash, version links, verification code |
| `service_drafts` | Saved, not-yet-submitted applications |
| `appointments` | Appointments linked to requests |
| `support_tickets`, `support_ticket_messages`, `support_ticket_attachments` | Support desk |
| `audit_logs` | Append-only audit trail |
| `otp_verifications`, `password_resets` | One-time codes and reset tokens (hashed) |
| `admin_mfa_factors` | Admin TOTP secret (encrypted) and recovery codes (bcrypt-hashed, then encrypted) |
| `account_recovery_requests`, `account_deletions`, `email_replacements` | Account recovery, deletion/restoration and email change |
| `verification_events`, `temporary_access_grants` | Manual verification ledger and time-limited access |
| `message_deliveries` | Email / SMS delivery log |
| `contact_messages`, `privacy_requests`, `security_incidents`, `settings`, `notifications` | Supporting records |
| `jobs`, `failed_jobs`, `cache`, `sessions` | Laravel infrastructure |

Database **triggers** created by the migrations make `audit_logs` and `verification_events` append-only
(no `UPDATE` or `DELETE`). They also protect temporary-access grants and the former-Admin marker. On
MySQL/MariaDB with binary logging, creating triggers can require the `TRIGGER` privilege, or
`log_bin_trust_function_creators=1`.

## Installation

**Requirements:** PHP 8.2 or later with the `pdo_mysql`, `mbstring`, `openssl`, `gd`, `fileinfo`, `zip` and `dom`/`xml`
extensions (and `pdo_sqlite` to run the tests), plus Composer 2 and MySQL 8 or MariaDB 10.6+. XAMPP works on Windows.

```bash
git clone https://github.com/<your-account>/e-notary-laravel.git
cd e-notary-laravel

composer install
cp .env.example .env          # Windows: copy .env.example .env
php artisan key:generate      # creates a NEW APP_KEY for your installation
```

Create an empty database (e.g. `enotary`), put its credentials in `.env`, then:

```bash
php artisan migrate
php artisan enotary:admin-create   # interactive: creates the first Admin (hidden password prompt)
php artisan serve                  # http://127.0.0.1:8000
```

Sign in as the Admin. With `ADMIN_MFA_REQUIRED=true` you are taken to two-factor enrolment first.

> No demonstration accounts or passwords ship with this repository. Create your own accounts locally.

## Environment configuration

Copy `.env.example` to `.env`. It contains placeholders only. **Never commit `.env`.** It is listed in
`.gitignore`. The settings that matter most:

| Variable | Meaning |
| --- | --- |
| `APP_KEY` | Generated by `php artisan key:generate`. Never reuse another installation's key |
| `APP_URL` | The exact address opened in the browser; email links are built from it |
| `DB_*` | Database connection |
| `TRUSTED_PROXIES` | Empty locally. `none` for a server that terminates TLS itself. Otherwise the proxy's IPs/CIDR (never `*`) |
| `LIVE_MAIL_ENABLED` | `false` (default) sends no email at all. `true` enables the allow-listed notification types |
| `LIVE_MAIL_RECIPIENTS` / `OUTBOUND_ALLOW_MAIL` | `allowlist` (default) mails only the listed addresses; `any` mails real registrants |
| `MAIL_MAILER`, `MAIL_HOST`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_FROM_ADDRESS` | SMTP settings (for Gmail, use an App Password) |
| `ADMIN_MFA_REQUIRED` | `true` makes Admin two-factor enrolment mandatory (recommended outside local development) |
| `ADMIN_REAUTH_MINUTES` | Step-up window for sensitive Admin actions (1-60, default 10) |
| `PROTECTED_ACCOUNTS` | Permanent Admin email address(es) that other Admins cannot edit, deactivate or delete; invalid entries are ignored |
| `CITIZEN_MOBILE_VERIFICATION_REQUIRED`, `MSG91_*` | Optional SMS verification; off by default |
| `SCHEDULER_SAFE_MODE` | `true` (default) registers only non-destructive scheduled tasks. `false` also runs the data-retention clean-up |

`deploy/production.env.template` is a commented production template, with placeholders only. Run
`php artisan enotary:deploy-check` on a server before opening the site.

## Testing

The tests never touch a real database or send real mail. `phpunit.xml` forces in-memory SQLite and fake
mail, queue, session and SMS drivers. `.env.testing` is intentionally empty, so no value from your `.env`
reaches a test, and `tests/TestCase.php` refuses to run if that isolation is missing.

```bash
php artisan test
# or
composer test
# Windows, with a dedicated storage folder for the run:
powershell -ExecutionPolicy Bypass -File scripts/Test-Isolated.ps1
```

The suite covers registration and verification, roles and policies, Notary approval, request workflow,
Admin MFA and step-up, rate limits, the outbound-mail gate, PDFs, the demonstration-claim guard, trusted
proxies, migrations and more. It has 1,600+ tests in `tests/Feature` and `tests/Unit`.

## Security and privacy notes

- Secrets live only in `.env`, which is never committed. `.env.example` and `deploy/production.env.template` contain
  placeholders only.
- Passwords are bcrypt-hashed. One-time codes, reset tokens and recovery codes are stored hashed, and the TOTP
  secret is encrypted with `APP_KEY`.
- Named rate limiters protect login, registration, OTP send and verify, password reset, contact, uploads,
  PDF generation and Admin writes.
- Security headers include CSP, `X-Frame-Options`, `Referrer-Policy` and `X-Robots-Tag`. Codes, tokens and
  passwords are never flashed back to forms, and they are redacted from mail logs.
- Uploaded documents are private and reachable only through authorised routes. Admin downloads require
  step-up.
- The audit log is append-only at the database level.
- To report a security issue in this project, please open a GitHub issue **without** exploit details and ask
  for a private contact.

## Limitations and future scope

**Current limitations**

- This is a demonstration only. There is no legally recognised notarisation, digital signature, e-stamp or
  identity verification (no Aadhaar/eKYC or DSC integration).
- SMS OTP is implemented but disabled, because Indian DLT registration was not completed for the demo.
- The demo runs on a free single-server host, with SMTP limited by the sending mailbox's daily quota.
- Documents are stored on the local disk, not in object storage. There is no virus scanning of uploads.
- No video-conference session for remote notarisation.

**Possible future work**

- PKI-based digital signatures and tamper-evident certificate signing.
- Integration with a recognised identity-verification provider.
- Object storage with encryption at rest and malware scanning.
- Remote audio/video session with recorded consent.
- Payments for service fees, and a public REST API (Sanctum is already installed).
- CI pipeline running the test suite on every push.
